# 加密空間與 ZIP 檔案管理：實作規劃

> 狀態：v0.3 功能原型已整合。ZIP 有串流、進度／取消、CRC 驗證與 Windows PowerShell 互通測試；加密空間具備復原金鑰、孤兒核對、密文資源回收筒、NanakoData 內備份／還原、進度／取消及加密媒體 Range。仍須獨立安全審查及磁碟滿載／強制中斷故障注入，不能視為正式安全保險箱。
> 日期：2026-11-05

## 目標與不可妥協的邊界

1. 所有受 Nanako 管理的來源、目的、暫存及資源回收桶路徑，均須限制在可攜式執行檔旁的 `NanakoData`；不可改選其他磁碟或 Windows 個人資料夾。
2. 加密空間必須讓磁碟上的上鎖檔案內容為密文。隱藏檔案、改副檔名或只設定 NTFS 權限都不符合需求。
3. ZIP 是封存／壓縮格式，不等於加密。v1 不以 ZIP 密碼取代加密空間。
4. 大檔案使用串流或固定大小區塊處理，不將完整影片、照片或封存檔讀進記憶體。
5. 任何新增套件只有在原型證實內建 Node.js/Electron 能力不足且完成授權審查後才採用；正式採用時才記錄版本、用途、授權與封裝狀態到 `THIRD_PARTY.md`。
6. 加密與壓縮的 UI 均在 Nanako 內部桌面／檔案管理視窗呈現，不呼叫 Windows Shell、不列出或管理 NanakoData 以外的路徑。

## 功能切分與建議順序

### A. ZIP 壓縮／解壓縮

目前只處理一般（未加密）的 Nanako 檔案；不讀取、解密或輸出加密空間中的物件。UI 於檔案管理器提供「壓縮 ZIP」與「解壓縮」動作，輸出位置與輸入選取範圍都只能在目前 Nanako 分享資料夾中。串流原型、伺服器端權限／路徑檢查與工作進度／取消已完成；每個封存最多 10,000 個項目、展開後 20 GiB。

建議流程：

1. 實作串流流程並量測記憶體；完成進度／取消、錯誤復原與 32 MiB ZIP 測試。
2. 驗證封存路徑正規化、符號連結拒絕、大小／數量上限、CRC／完整性錯誤及 Windows PowerShell `Compress-Archive`／`Expand-Archive` 互通。
3. 建立 ZIP 時逐項串流至同目錄的隨機暫存檔；成功完成並關閉後再原子改名。失敗、取消或磁碟空間不足時刪除暫存檔，不留下看似完整的 ZIP。
4. 解壓縮時先列出並驗證每個項目，拒絕絕對路徑、磁碟代號、UNC 路徑、`..`、符號連結及重複／衝突路徑。預設建立新的目的資料夾，不覆寫現有檔案。
5. 將解壓縮內容先寫入 NanakoData 內的隔離暫存目錄；所有項目通過 CRC、限制及路徑驗證後，才將整個結果移入目的資料夾。取消或失敗要完整清除暫存結果。
6. 加入可取消進度、已處理項目數／位元組、明確錯誤訊息及管理員／使用者權限檢查。伺服器端重新驗證每個操作，不只依賴 UI 隱藏按鈕。（已完成原型）

安全測試至少涵蓋 ZIP Slip、絕對／UNC／磁碟路徑、符號連結、重複檔名（含 Windows 不區分大小寫的衝突）、惡意高壓縮比、超多項目／超深路徑、截斷檔、錯誤 CRC、未知壓縮方法、取消及磁碟空間不足。

#### ZIP 套件採用狀態

- 已採用 [zip.js](https://github.com/gildas-lormeau/zip.js) `@zip.js/zip.js` 2.24.0（BSD-3-Clause）實作串流 ZIP 建立與解壓，支援 Zip64 與隨機讀取；授權及封裝資訊列於 `THIRD_PARTY.md`。
- 本版未採用 JSZip、Archiver 或 yauzl，亦未複製其原始碼。
- 已驗證一般檔案建立／解壓、ZIP Slip 拒絕、修改內容後 CRC 拒絕／暫存清理、32 MiB 隨機內容串流記憶體測試、取消清理及 PowerShell 封存互通。更大型檔案／不同 Windows 環境效能、多類損毀格式及磁碟寫入故障注入仍待驗證。

### B. 加密空間／檔案上鎖

建議把加密空間視為 NanakoData 內獨立的物件儲存區，而不是在原目錄旁放一份明文加鎖副本。一般檔案仍維持一般檔案；使用者明確執行「移入加密空間／上鎖」才轉換。

#### 建議的資料與金鑰模型（待 ADR 與威脅模型確認）

- 每個 Nanako 使用者有自己的加密空間金鑰；預設不提供管理員繞過，也不默認分享解密權。跨使用者共用若有需求，另設明確授權及金鑰包覆流程。
- 使用密碼透過 Node.js 內建 `scrypt` 派生金鑰加密（wrap）隨機產生的 vault master key；使用者密碼不直接當作檔案加密金鑰。scrypt 參數需依最低支援 Windows 電腦效能量測並版本化。
- 使用 Node.js 內建 `crypto` 的 AES-256-GCM 作為候選認證加密方式。每個物件使用獨立隨機識別值與金鑰材料；大型檔案切成固定大小區塊，每區塊獨立驗證，採用經審查的唯一 nonce 配置，並將物件識別值、格式版本、區塊索引等納入 AAD。
- 檔名、相對路徑、MIME、原始大小、時間戳記與其他敏感索引一併加密；磁碟上只保留不透明隨機物件名稱及必要的非敏感格式欄位。SQLite 中敏感中繼資料只可存加密內容。
- 上鎖後，Windows 檔案總管可看到的至多是 Nanako 加密容器密文，不應從磁碟檔名、縮圖快取、暫存檔、SQLite 或日誌還原明文名稱及內容。
- 金鑰只留在 Node 主程序的受控執行期記憶體，不傳給 Renderer。登出、手動鎖定、逾時或應用程式關閉時清除可清除的 Buffer／金鑰參照；需明確說明 JavaScript 執行環境無法保證所有複本都立即從記憶體抹除。
- 不提供管理員密碼重設來解密 vault。初次建立時產生一次性復原金鑰並只顯示一次；使用者可在已解鎖狀態輪替。若遺失密碼與復原金鑰，資料可能永久無法解密。復原金鑰本身需由使用者離線保管。

#### 已整合的加密空間原型

- `src/vault-crypto.mjs` 已接至本機 API 與 Nanako 內部視窗。Envelope 以 scrypt（`N=32768, r=8, p=1`）衍生包覆金鑰，再以 AES-256-GCM 包覆隨機 master key；AAD 綁定 Nanako 使用者 ID。KDF 參數由格式版號固定，不接受封裝檔自行指定高成本參數。
- 每個物件依 master key、使用者 ID 與隨機 UUID 透過 HKDF-SHA-256 派生獨立內容／中繼資料金鑰。新寫入內容採 128 KiB AES-256-GCM 區塊（解碼器仍接受早期 v1 原型寫入的 1 MiB 記錄）、4-byte 隨機 nonce 前綴加 64-bit 大端序計數器；AAD 綁定格式版本、物件 UUID、nonce 前綴、區塊序號及長度。新物件必須使用全新 UUID。
- 最後一筆是經認證的空終止區塊；缺少結尾、內容遭竄改、識別值不符或有尾隨資料都拒絕。每個資料區塊只有在 `decipher.final()` 驗證成功後才會交給呼叫端。
- UI 僅能瀏覽有寫入權限的 Nanako 資料空間，不會呼叫 Windows 資料夾挑選器。移入流程先串流加密、二次解密雜湊驗證、儲存密文與加密索引，成功後才移除來源路徑；中途錯誤會保留來源並清除暫存。SQLite 不保存明文名稱、相對路徑、MIME 或大小。
- 索引交易會同時建立 `vault_pending_imports` 標記。程序若在索引完成後、來源移除或標記清除前中止，解鎖後的復原畫面會比對加密中繼資料內的來源識別值與 SHA-256；只有仍在 NanakoData 且內容相符時才提供使用者確認移除，來源已變更時拒絕刪除。也可只清除待處理標記、保留明文與密文兩份。標記不保存明文路徑。未索引密文採 sidecar 核對與逐區塊解密驗證，僅驗證成功的物件可由使用者確認採用，其他孤兒須明確確認清理。
- 圖片、音訊與影片可在 Nanako 內透過 API 解密串流預覽／播放，支援 HTTP byte-range，不建立明文暫存檔；其他檔案格式目前只可加密保存。清單只在解鎖後呈現，登出、手動鎖定、密碼變更、帳號停用、閒置 15 分鐘或服務關閉時撤銷金鑰參照。錯誤密碼 5 次後節流 15 分鐘。
- 復原金鑰、孤兒檔核對、密文回收桶、NanakoData 內密文備份／還原、大檔案串流量測、進度／取消，以及 Range／並行播放器原型已納入。仍需獨立格式安全審查、測試向量、格式升級相容性與磁碟故障／強制中斷注入；SQLite 與檔案系統沒有共同交易，SSD 舊區塊也不保證安全抹除。
- 依 Node.js `crypto` 與 NIST SP 800-38D 文件選用內建 API，未新增第三方套件；nonce/key 管理與容器格式仍需獨立審查。[Node.js Crypto](https://nodejs.org/api/crypto.html) [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)

#### 加鎖轉換與使用流程

1. 「建立加密空間」先建立格式版本、隨機 vault key、salt、驗證標記及金鑰包覆資料。只顯示必要的復原資訊，不在資料夾中另存明文金鑰。
2. 「移入加密空間」只接受 NanakoData 內檔案。從來源串流加密到 vault 內隨機暫存物件，完成後重新解密驗證雜湊，再寫入加密 sidecar、發布密文及加密索引；所有步驟成功後才移除原明文來源。中途失敗時原檔保持不變並清除不完整密文暫存。索引提交後的突然中止由 pending 標記提供人工復原；索引交易前的孤兒由 sidecar 在解鎖後核對，不會自動收編。
3. 鎖定狀態下檔案清單顯示最少必要資訊，或完全隱藏 vault 內項目；解鎖後依 Nanako 帳號權限呈現解密後名稱與中繼資料。
4. Nanako 內圖片預覽及影音播放以受授權 API 串流解密區塊至記憶體，不產生明文暫存檔。HTTP Range 必須對應並驗證相關加密區塊，再由伺服器提供所需明文字節。
5. 加密空間中的刪除／資源回收桶仍儲存密文；還原僅更新 Nanako 內索引，不解密落地。永久刪除密文不等於保證安全抹除 SSD 備援區塊。
6. 一般檔案下載或匯出可能產生明文，因此 v1 預設不在加密空間提供下載／匯出；若未來增加，必須明確提示解密結果並維持使用者所選的 Nanako 管理範圍。不得新增外部資料夾瀏覽或任意磁碟目的地。

#### 主要威脅與不承諾事項

本功能的目標是讓未解鎖時取得 NanakoData 儲存內容的人只能讀到密文，並讓 Windows 檔案總管無法直接開啟原始檔。它不能防止已登入且 vault 已解鎖時的螢幕擷取、鍵盤側錄、管理員／核心層級程式、惡意程式、記憶體擷取、已授權使用者複製內容或使用者自行匯出明文。加密也不取代備份。復原、密碼忘記與應用程式更新相容性須有明確 UX 和測試。

### C. 加密與 ZIP 的整合順序

1. ZIP v1 僅作用於一般 Nanako 檔案，不能把 vault 的密文再次當作普通檔案壓縮，也不能因解壓縮而產生 vault 明文。
2. 加密空間 v1 先支援受控檢視／播放，不與壓縮互通。
3. 後續若支援 vault 壓縮，輸入必須在伺服器端解密串流，封存輸出應直接串流加密進 vault；解壓縮則先驗證封存再逐項加密寫入 vault。不可在磁碟上短暫產生明文 ZIP 或明文解壓目錄。

## 目前已實作的 API 與 UI 原型

操作一律採已登入使用者的本機授權、伺服器端路徑驗證及 NanakoData 固定根目錄；正式對外 API 版本仍未規劃。原型路由包括：

- `POST /api/vault/setup`、`POST /api/vault/unlock`、`POST /api/vault/recover`、`POST /api/vault/lock`、`GET /api/vault/status`
- `POST /api/vault/password`、`POST /api/vault/recovery-key`、`GET /api/vault/objects`、`POST /api/vault/objects/import`、`GET /api/vault/objects/import/status`、`POST /api/vault/objects/import/cancel`
- `GET /api/vault/trash`、`POST /api/vault/trash/:id/restore`、`DELETE /api/vault/trash/:id`、`GET|POST /api/vault/backups`、`POST /api/vault/backups/:id/restore`、孤兒核對／清理端點
- `POST /api/archive/create`、`POST /api/archive/extract`、`GET /api/archive/status`、`POST /api/archive/cancel`

上述為內部本機 API，UI 顯示目前狀態、操作進度、Nanako 資料空間範圍、取消結果及加密／壓縮的差異。正式對外 API 名稱與生命週期仍留待後續版本設計。

## 驗收與測試門檻

### 加密

- 錯誤密碼、篡改密文、截斷／重排／替換區塊、錯誤格式版本都必須失敗封閉，不回傳未驗證明文。
- 以不同 Nanako 帳號測試隔離；鎖定、登出、閒置逾時、重啟、電腦休眠／喚醒後金鑰狀態符合規格。
- 用可辨識測試檔案檢查整個 NanakoData：密文物件、資料庫、縮圖、快取、日誌、回收桶與暫存區不得留下原始檔內容或名稱。
- 以大檔案量測記憶體峰值為固定區塊級而非檔案大小級；測試中止、程式強制結束、磁碟已滿及寫入錯誤時，原檔／索引一致且不留下假成功狀態。
- 驗證加密檔案相片與 Range 影音播放不產生明文檔案；測試區塊邊界、seek、並行讀取及權限撤銷。
- 對格式實作做獨立程式碼審查及測試向量驗證；未完成前不把功能標示為安全保險箱或正式加密。

### ZIP

- 大量檔案／大檔案串流測試、取消測試與 Windows Explorer 開啟測試。
- ZIP Slip、符號連結、zip bomb、重複路徑、CRC 損壞、截斷檔及未知壓縮方法等拒絕測試。
- 任一錯誤或取消不留下部分可被誤認為完成的 ZIP／解壓資料夾；不覆寫既有檔案。
- 伺服器以 canonical path、資料夾 ID 與權限重新驗證，不依信任 Renderer 提供的任意路徑。

## 不在這一階段做的事

- 不加入 SSO、雲端同步、遙測、硬體控制或 Windows 系統資料夾整合。
- 不讓檔案管理器讀取或寫入 NanakoData 以外路徑。
- 不以 ZIP 密碼取代具認證加密的 vault。
- 未完成串流和威脅測試前，不做轉檔、明文暫存、跨使用者共享解密或管理員後門。
- ZIP 第一版不支援密碼加密或 vault 整合；解壓縮前會拒絕加密 ZIP。

# ADR-0009：加密空間設計原則

- 狀態：原型已整合 UI／API；格式及資料復原決策仍為暫行，未達正式產品安全門檻
- 日期：2026-11-05

## 背景

使用者要求加密空間及檔案上鎖後，即使從 Windows 檔案總管直接開啟 NanakoData 中的儲存物件，也只能取得密文。Nanako 的檔案、相簿、影音、壓縮與資源回收桶都受限於可攜式資料範圍。

## 提案

1. 將加密空間建成 NanakoData 內獨立的密文物件儲存區；一般檔案除非使用者明確移入，否則不受影響。
2. 採隨機 vault master key，由以使用者密碼經 scrypt 派生的包覆金鑰保護；檔案內容候選採 Node.js 內建 AES-256-GCM 與固定大小認證區塊。
3. 檔名、路徑、MIME 與大小等敏感中繼資料加密；物件檔名使用隨機、不透明識別值。
4. 每個 Nanako 使用者預設使用獨立金鑰，管理員不具有隱含解密權；共享解密若有需求另行提出 ADR。
5. 解密只在 Nanako 主程序授權後串流至 Nanako UI，不落地明文暫存檔。上鎖／登出／逾時後撤銷可用金鑰參照。
6. 加鎖轉換以暫存密文、驗證、索引交易、最後才移除來源明文的順序執行；失敗不得造成來源遺失或假成功。

## 考量與限制

- Node.js 內建 `crypto` 可以避免為基本加密新增執行期套件，但不代表自行設計容器格式自然安全；區塊 nonce、AAD、版本遷移、驗證失敗行為及復原流程都要先經審查。
- JavaScript 記憶體清除只能盡力而為，不能保證 GC、複製或作業系統記憶體分頁中的所有金鑰複本都即刻消失。
- 無復原金鑰時遺失密碼可能永久失去資料；管理員重設帳號密碼不能順便重設 vault 金鑰。
- 已解鎖期間的螢幕擷取、惡意程式、具系統管理員／核心權限的使用者不在本功能可防護範圍。
- SSD 上刪除明文不保證可安全抹除所有舊區塊；因此上鎖流程不宣稱符合安全抹除。

## 替代方案

- 僅以 UI 隱藏或 NTFS ACL 保護：無法滿足檔案總管直接讀取時仍只見密文的要求，拒絕。
- 整個資料夾採單一 ZIP 密碼：無法滿足可靠認證加密、串流媒體與個別權限需求，不作為 vault 方案。
- 自製未經驗證的密碼學或容器格式：不接受；必須使用成熟原語、明確格式版號、測試向量與獨立審查。

## 已整合的原型範圍

- `src/vault-crypto.mjs` 使用 Node.js 內建 scrypt（`N=32768, r=8, p=1`）包覆隨機 master key；使用者密碼不直接作為檔案金鑰。Envelope 以 AES-256-GCM 保護，AAD 綁定 Nanako 使用者 ID。
- 每個不可變物件由 master key、使用者 ID、隨機物件 UUID 透過 HKDF-SHA-256 派生不同的內容與中繼資料金鑰。內容採 1 MiB AES-256-GCM 區塊串流，AAD 綁定格式版號、物件識別值、nonce 前綴、區塊序號及長度；最後使用經認證的空終止區塊偵測截斷與尾隨資料。
- NanakoData 內的「移入並上鎖」只接受既有 Nanako 分享中的一般檔案。伺服器先串流加密並以解密雜湊驗證，再寫入不透明 UUID 密文物件、加密名稱／相對路徑／大小／MIME 索引，最後移除原始檔案路徑；失敗時會保留來源並清除本次暫存。SSD／檔案系統可能保留舊資料區塊，不承諾安全抹除。
- 只有該使用者解鎖後，才可透過 API 查看解密後清單；圖片、音訊、影片透過已驗證區塊串流給 Nanako renderer，支援 HTTP byte-range，沒有明文暫存檔。未知格式暫不提供預覽。Renderer 不會收到 master key。
- 登出、手動鎖定、密碼變更、帳號停用、閒置 15 分鐘及服務關閉會取消並清理執行中的加密／解密串流，再撤銷可用金鑰參照。錯誤密碼 5 次後依來源位址與帳號節流 15 分鐘。解鎖狀態與金鑰只存在程序記憶體。
- 移入流程會在同一個 SQLite 交易建立密文物件索引與不含路徑的 `vault_pending_imports` 標記，來源移除後才刪除標記。若在來源移除／標記清除間意外中止，解鎖後可查詢復原清單；只有來源雜湊與已加密內容一致時才允許使用者確認移除，來源已變更時強制保留。錯誤或被拒絕的來源不會自動刪除。
- 單元／整合測試已涵蓋錯誤密碼、跨使用者、格式與中繼資料篡改、跨物件替換、內容篡改、截斷／尾隨資料、多區塊與空檔案、僅限 NanakoData、來源檔案移除、密文／索引不洩漏檔名、Range 播放及錯誤密碼節流。

## 尚未達到正式產品門檻

這仍是未完成的產品原型，不應宣稱為正式安全保險箱，也不應存放唯一副本或實際機密資料。內容格式與 key／nonce 生命週期須完成獨立審查和測試向量驗證。Node.js 文件指出，GCM 驗證必須在 `decipher.final()` 成功後才成立；NIST SP 800-38D 指出 GCM 的 IV／nonce 管理是安全條件。[Node.js Crypto](https://nodejs.org/api/crypto.html) [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)

尚待完成：復原金鑰與備份／復原 UX、密文發布至索引交易前的未索引孤兒檔清理、大檔案記憶體／磁碟量測、取消與進度、損毀／磁碟滿載測試、播放器 seek／並行請求、索引遷移及獨立安全審查。`decipher` 僅在各區塊驗證成功後交出該區塊；Range 播放只會驗證本次讀取到的區塊，不會在每次 seek 時重驗整個物件。JavaScript 記憶體清除僅盡力而為，不能保證 GC、複製或作業系統記憶體分頁中的所有金鑰複本都即刻消失。

加鎖轉換涉及檔案系統與 SQLite，兩者沒有共同交易。索引提交與來源移除間的中止目前以 SQLite 復原標記和解鎖後人工確認處理；若在密文發布後、索引交易前突然中止，可能留下未索引密文孤兒檔，尚未完成啟動核對。仍須加入該類故障注入、重啟復原測試，不能以一般成功路徑測試代替。

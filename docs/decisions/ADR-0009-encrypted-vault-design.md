# ADR-0009：加密空間設計原則

- 狀態：提案，進入實作前需完成威脅模型與格式原型
- 日期：2026-11-05

## 背景

使用者要求加密空間及檔案上鎖後，即使從 Windows 檔案總管直接開啟 NanakoData 中的儲存物件，也只能取得密文。Nanako 的檔案、相簿、影音、壓縮與資源回收桶都受限於可攜式資料範圍。

## 提案

1. 將加密空間建成 NanakoData 內獨立的密文物件儲存區；一般檔案除非使用者明確移入，否則不受影響。
2. 採隨機 vault master key，由以使用者密碼經 scrypt 派生的包覆金鑰保護；檔案內容候選採 Node.js 內建 AES-256-GCM 與固定大小認證區塊。
3. 檔名、路徑、MIME 與大小等敏感中繼資料加密；物件檔名使用隨機、不透明識別值。
4. 每個 Nanako 使用者預設使用獨立金鑰，管理員不具有隱含解密權；共享解密若有需求另行提出 ADR。
5. 解密只在 Nanako 主程序授權後串流至 Nanako UI，不落地明文暫存檔。上鎖／登出／逾時後撤銷可用金鑰參照。
6. 加鎖轉換以暫存密文、驗證、索引交易、最後才移除來源明文的順序執行；失敗不得造成來源遺失或假成功。

## 考量與限制

- Node.js 內建 `crypto` 可以避免為基本加密新增執行期套件，但不代表自行設計容器格式自然安全；區塊 nonce、AAD、版本遷移、驗證失敗行為及復原流程都要先經審查。
- JavaScript 記憶體清除只能盡力而為，不能保證 GC、複製或作業系統記憶體分頁中的所有金鑰複本都即刻消失。
- 無復原金鑰時遺失密碼可能永久失去資料；管理員重設帳號密碼不能順便重設 vault 金鑰。
- 已解鎖期間的螢幕擷取、惡意程式、具系統管理員／核心權限的使用者不在本功能可防護範圍。
- SSD 上刪除明文不保證可安全抹除所有舊區塊；因此上鎖流程不宣稱符合安全抹除。

## 替代方案

- 僅以 UI 隱藏或 NTFS ACL 保護：無法滿足檔案總管直接讀取時仍只見密文的要求，拒絕。
- 整個資料夾採單一 ZIP 密碼：無法滿足可靠認證加密、串流媒體與個別權限需求，不作為 vault 方案。
- 自製未經驗證的密碼學或容器格式：不接受；必須使用成熟原語、明確格式版號、測試向量與獨立審查。

## 後續工作

完成威脅模型、vault 使用者／共享權限定案、密碼與復原 UX、區塊格式原型、篡改測試、記憶體峰值測試及崩潰復原測試後，才可將提案轉成已接受決策並開始功能實作。
